# Browser and computer use

Use only the tools named here.

If you go around a rule in this skill, quote its stated reason when you report that, and ask one direct question.

## Browser

Use Vercel Labs' `agent-browser` from the shell for browser automation, verification, and web development testing on every host, in both Claude Code and Codex. Once per session, load the guide that ships with the installed CLI: `agent-browser skills get core`, adding `--full` for the command reference. Load a specialised guide from `agent-browser skills list`, such as `electron` or `dogfood`, when the task matches it. This shared policy supplies host routing and session ownership; the CLI's guide supplies commands. Where they disagree, follow this policy. Run repository test suites, including Playwright Test suites, through the repository's documented commands.

- Run the installed Google Chrome on every host, never Chrome for Testing, and never run `agent-browser install`. The dotfiles pull sets `executablePath` in `~/.agent-browser/config.json` to it. Where that file or key is missing, pass `--executable-path <installed Chrome>` on `open`, such as `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"` on macOS.
- Inside a Codex workspace-write sandbox, point `AGENT_BROWSER_SOCKET_DIR`, `TMPDIR`, `XDG_CONFIG_HOME` and `XDG_CACHE_HOME` at folders in the workspace, keep `--profile` there, and pass `--executable-path` as the bullet above says.
- Add a random suffix to every session name, because `agent-browser session id` derives the same name for every agent in one checkout.
- Close only the sessions you opened, each by name: `agent-browser --session <name> close`.
- Diagnose with `agent-browser doctor`, and leave its `--fix` repairs to the user, because they touch state that other sessions share. Without `--fix` it removes only stale daemon socket, pid and version files, so a queued check can run while other sessions work.
- An idle headless session closes after an hour and discards its tabs. Pass `--idle-timeout <time>` on `open` when a human needs longer.
- Some sites refuse a user agent that says `HeadlessChrome`. Pass `--user-agent 'Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/<major>.0.0.0 Safari/537.36'`, with the installed Chrome's major version, on every command, as the launch-flag bullet below says.
- On a heavy page, `open` can fail with "CDP command timed out: Page.navigate" or "no response came back" while the page goes on loading. Read the page's state, such as `get url` or a snapshot, before you treat the `open` as failed.
- A session opened with launch flags, such as `--profile`, `--headed` or `--idle-timeout`, keeps its browser only while every later command passes the same flags, `get url`, `tab list` and `close` included. A command that leaves one out or changes its value restarts the browser and loses the profile's sign-in. On macOS and Linux, run every command through `scripts/ab_session.py`, which saves the flags once per session. On Windows, pass the same flags on every command. Chrome lets one process use a profile folder, so check that the user's own Chrome isn't running on a profile before you pass it to `--profile`.
- Write screenshots, PDFs, HAR files and recordings to explicit paths in a scratch directory.
- To render or screenshot a page at a set width, measure its layout with `scripts/page_check.py`, test hover styles, run a probe that waits on the page's timers, or download files, read [references/page-checks.md](references/page-checks.md).
- Give a Chrome you start, and a socket such as `cua-driver serve --socket`, a short path, such as a folder from `tempfile.mkdtemp()` under `/tmp`, because a Unix socket path must stay under about 108 bytes.
- A harness's own HTML preview tool, such as T3 Code's `html_preview`, is for showing the user a result. To check a page's behaviour or its layout at set widths yourself, open the file with agent-browser at `file://<path>`.
- After inspecting the page, run a known sequence of related actions in one `batch --bail` call. Write the steps to a scratch JSON file as an array of argument arrays, such as `[["fill", "#email", "a@example.test"], ["click", "#save"], ["wait", "--text", "Saved"], ["get", "text", "#status"]]`. Pass the file on standard input: `agent-browser --session <name> batch --bail < steps.json`, or in PowerShell `Get-Content -Raw steps.json | agent-browser --session <name> batch --bail`. The JSON form survives shell quoting on every host. End with the expected wait and a check of the resulting state. Keep a snapshot checkpoint whenever the next action depends on what the page shows.
- In an app with single-key shortcuts, such as mail, send input to a named element inside the `batch --bail` call. Page-level `keyboard type` and `press` go to whatever has focus, so after a failed click they can trigger the app's shortcuts.
- On Windows, pass JavaScript that holds a line break through `eval --stdin`, because the mise and npm launchers reject or cut off an argument that holds one.
- Change the agent-browser version only through the dotfiles mise pin, as Maintenance describes.
- When agent-browser prints "Daemon version mismatch detected, restarting", read [references/maintenance.md](references/maintenance.md) before you sign in again.

Host notes:

- For an existing sign-in, inspect `agent-browser session list` and known task profiles first, and reuse only a session this task owns. Attach to the user's own Chrome or its profile (`--auto-connect`, `--cdp` or `--profile <profile-name>`) only when the user asks for it in this task, because it holds their signed-in sessions. The private `e-conomic-ledger-read` skill's read-only search is an exception the user chose on 2026-11-14: a task that needs it opens or attaches to their profile and says so in the same message, and that choice counts as their yes to its attach below. When the user has turned remote debugging on at `chrome://inspect`, click Chrome's "Allow remote debugging?" prompt only after they said yes to attaching in this task, and only for a connection you opened. When you finish, offer to turn remote debugging back off, and name any other task that uses it. When sign-in is required, keep a dedicated profile directory for it. Google refuses "Sign in with Google" in a browser under automation, so the human signs in once in plain Chrome started without agent-browser. Start it with `--user-data-dir=<directory> --use-mock-keychain --password-store=basic --no-first-run --no-default-browser-check <url>`, which matches the keychain and password store that agent-browser uses. On macOS that is `open -na "Google Chrome" --args` followed by those flags, and elsewhere the installed Chrome with them. Those two flags belong to a profile directory of your own. The user's own Chrome profile on Linux keeps its cookies in the system keyring (cookie values start with `v11`), so start it without them, because with them it opens signed out. Chrome started on that profile while the keyring is locked deletes every cookie it can't decrypt, so start it only after `python3 -I scripts/chrome_keyring.py check` exits 0, and on exit 1 pass its unlock command on to the user. `read_page.py` and the private `x-browser` skill run that check before they start Chrome. To check that profile's sign-in without starting Chrome, copy its `Default/Cookies` file to a scratch path and look for the site's session cookie names, such as LinkedIn's `li_at`. Once the human has quit that Chrome, reuse its sign-in with `agent-browser --session <name> --profile <directory> open <url>`. Keep profiles, state files and `--restore` state outside repositories and evidence, and keep cookies and tokens out of output.
- To attach to the user's running Chrome with `--auto-connect`, after their yes, read [references/attach.md](references/attach.md) first.
- When WebFetch, curl or headless agent-browser meets a 403, a Cloudflare check or another bot wall on a page you only read, read [references/bot-walls.md](references/bot-walls.md) for the routes that show nothing on the user's desktop. A `--headed` agent-browser session passes many bot walls. On WSL, try one on the hidden display first, without asking, the user's choice on 2026-11-14: `env -u WAYLAND_DISPLAY DISPLAY=:99 scripts/ab_session.py start NAME --headed -- open URL`. Ask the user before a `--headed` window that opens on their desktop. If the page still won't load, ask the user whether to read it in their own Chrome with `scripts/read_page.py`. For a file a deliverable will quote, such as a PDF, make the same offer before you settle for an abstract or a weaker source, because the user's own Chrome often passes the check unaided. Tell the user which facts you could not read at the source instead of filling them from third-party summaries.
- Public X or Twitter posts and long articles need no browser. `curl -s https://api.fxtwitter.com/status/<id>` returns one as JSON with no login, with a long article's text under `tweet.article.content.blocks`. It is a third-party service, so check that the JSON's `code` is 200, and open an agent-browser session when it is down.
- Paywalled news sites, such as the FT and The New York Times, block DevTools automation, agent-browser included, with bot checks even after the user passes them by hand. On every host, read them with the user's subscriptions through their own Chrome profile and `cua-driver`'s accessibility tree, without asking first. This and the e-conomic exception above are the only uses of their profile that need no request in the task. Never attach DevTools to this profile, through `browser_prepare` or agent-browser, even when `cua-driver` would allow it, because those bot checks block it.
- To read a paywalled news page, or any page the user asks you to read in their own Chrome, read [references/read-page.md](references/read-page.md) before you run `scripts/read_page.py`. Open no URL in the user's Chrome with `cua-driver launch_app` and `urls`, which adds a tab to their front window. When one Chrome profile holds several accounts of an app, open the app with an account hint, such as `https://outlook.office.com/mail/?login_hint=<address>`, and assert the signed-in address on the page before the first search or capture.
- agent-browser runs Chrome on the host where the command runs, so `localhost` reaches that host's dev servers. Windows Chrome also reaches WSL dev servers on `127.0.0.1` through mirrored networking.
- On WSL, Windows Chrome and WSL's Chrome are separate browsers, each with its own network and profiles. When a read through Windows Chrome returns nothing, test the Windows host's network with a TCP check through interop, such as `powershell.exe -NoProfile -Command '(Test-NetConnection example.com -Port 443).TcpTestSucceeded'`, before retrying with longer waits. Send no web request from Windows for this, such as `curl.exe` or `Invoke-WebRequest`, because endpoint security can flag it and isolate the machine. Then try a `--headed` agent-browser session in WSL on the hidden display `:99`, as above, before you report the page as blocked. Tell the user before you use a host or profile other than the one they approved.
- Approval to use a signed-in profile covers the sites the user named. Open any other site in a dedicated profile of your own, or ask first, because every page that profile loads runs beside its signed-in sessions.
- To open a dev server from another host, use an existing task-owned tailnet share or run `tailscale serve <port>` in the foreground. Record the process ID and printed URL. Stop only that process when finished and confirm its URL no longer loads; a foreground share is absent from `tailscale serve status`. For a share that outlives the session, such as one for the user's phone, follow `work-across-tailscale-machines`.
- Codex's in-app browser (`iab`) exists only inside the Codex desktop app.
- Windows: before you start an agent-browser session, in a native shell or over SSH, read [references/windows.md](references/windows.md).
- To drive an Electron app, or a Chrome this task started with remote debugging, read [references/cdp.md](references/cdp.md).

## Computer use

Prefer a CLI, an API, or the browser tools when they can do the job. Use desktop control only for native apps and for reading pages in the user's own Chrome, as the browser host notes describe. When a value exists only in an app's window, or you are about to give the user click steps, drive the app yourself, including to clean up a tool you installed. Before you say a product lacks a control or that you can't reach one, look at its other surfaces, such as its desktop app, its config file, its local install and the Windows-side driver, and name the ones you checked in that sentence. That covers a consent or permission prompt inside an action the user has approved: say what the prompt grants, offer in the same message to click it yourself, and act on their yes. Before you ask the user to paste or retell mail or chat content, offer to read it in the app, and wait for their yes because it is private. If an app you launched shows no accessibility tree, check your own launch first: an app started inside its own `dbus-run-session` shows none until accessibility is enabled on that bus (`org.a11y.Status` `IsEnabled`, `ACCESSIBILITY_ENABLED=1`) and cua-driver runs with the same `DBUS_SESSION_BUS_ADDRESS`.

- macOS and Windows: before you drive an app with `cua-driver`, read [references/cua-driver-hosts.md](references/cua-driver-hosts.md). Do not start a second daemon or use Codex Computer Use as a fallback.
- Linux (WSL): the open-source `cua-driver` server's MCP tools, called directly; the `cua-driver` CLI depends on a background service that is stopped here. Its own `cua-driver` skill documents the tools. The server draws on a private virtual display (`:99`), hidden from the user along with any app you launch there. To drive an app on the Windows desktop from WSL, run `cua-driver.exe call <tool> '<json>'` through interop instead. Its guide is at `/mnt/c/Users/<user>/.claude/skills/cua-driver/WINDOWS.md`, because the WSL install carries only the Linux guide.
  - To read or drive a window the user sees, a WSLg window on display `:0` such as their Chrome, read [references/wslg.md](references/wslg.md) first. It covers a second `cua-driver` on `:0`, AT-SPI actions, Chrome on `:0`, and clicking, pasting and reading back through `cua-driver.exe` from the Windows side.
  - Send input only through the routes this skill and that file name. Raw input, such as XTEST through ctypes or `xdotool type`, goes to whichever window has focus, not to your target, and so does `cua-driver.exe` in foreground delivery, which reports success while the keystrokes land elsewhere, such as in Windows' Start search. Stop after the first input with no visible effect, and find out where it went before you send more.
- A loop that polls a window or page, or an agent-browser loop that measures one page after another, checks each step's exit status and that the window ID or URL is still its target before it counts the result. A failed capture that recopies the last image makes a dead window look idle, a session moved to another tab reports a false finish, and a failed `open` leaves the previous page loaded, so assert `location.pathname` on every row and count the distinct pages measured against those expected.
- Leave a window the user already has open as it is, even when it is stuck. To get past a stuck state such as a PIN dialog, open a temporary window of your own, because a reload can leave theirs blank.
- Windows apps:
  - For admin-only programs, Store apps, toggles in a WebView2 app, pixel clicks, virtualised lists in a Chromium or WebView2 app, and vendor settings, read [references/windows.md](references/windows.md).
  - Electron apps with no accessibility tree, such as the Claude desktop app, which is how a message reaches an agent session running there. Read it with `get_window_state` and `include_accessibility_tree:false`, and read again when the capture times out. Put text into its message box with `python3 -I scripts/win_paste.py --pid <pid> --window-id <id> --x <x> --y <y> < file` from WSL, with `--replace` when the box may hold text and with a time limit of 4 minutes; its `--help` gives its exit statuses and what it does with the user's clipboard. It brings the window to the front for a moment, so first run `win-presence --away-after 5` on WSL, which reads whether the user is at the PC; the user chose 5 idle minutes on 2026-11-15 over 15, accepting that a user reading the screen gives no input. On exit 3, away, paste without asking. On exit 0, present, or any code other than 0 and 3, which counts as unknown, ask through the question tool and wait for the user's word that they are not typing, because a user at the desktop is not reading the chat. Then look at the window and click the app's send button in the background. Leave `type_text` in the foreground alone there: it stopped after 224 of 799 characters when the user clicked another window.
  - Key combinations: a background `hotkey` can report success while the window receives the letters alone. A WinForms text box received "av" for Ctrl+A and Ctrl+V on 11 November 2026, so read the field back. The driver's own guide says to try the background first and go to the foreground only on a refusal, which this case never gives, so where the window has no tree to read back, pass `delivery_mode:"foreground"` for the combination from the start.
  - Foreground input: a foreground `scroll` or key goes to whichever window is in front when it arrives. Run `win-presence --away-after 5` first, as for `win_paste.py` above: on exit 3 send the input without asking, and on any other code only after the user's word, since every code other than 0 and 3 counts as unknown. Send it in one `run_steps` call right after `bring_to_front` on the target, and check that `landed_on_target` is true. After typing, capture the window again a few seconds later before you type again, because a capture can show the screen from before the input.
  - A test window: Windows 11's Notepad reopens the files of its last session, so a Notepad you launch can show the user's documents, and a read of its tree returns their text. Test input in a window of your own instead, such as a PowerShell `System.Windows.Forms` form with one `RichTextBox`.

## Maintenance

The durable source is `skills/browser-and-computer-use` in the dotfiles checkout. Maintain it there and refresh its reviewed source lock before device sync.

Before you upgrade agent-browser, Chrome or cua-driver, change this skill's scripts, or measure a CLI workflow change, read [references/maintenance.md](references/maintenance.md).
