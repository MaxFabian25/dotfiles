# Browser and computer use

Use only the tools named here.

## Browser

Use Vercel Labs' `agent-browser` from the shell for browser automation, verification, and web development testing on every host, in both Claude Code and Codex. Once per session, load the guide that ships with the installed CLI: `agent-browser skills get core`, adding `--full` for the command reference. Load a specialised guide from `agent-browser skills list`, such as `electron` or `dogfood`, when the task matches it. This shared policy supplies host routing and session ownership; the CLI's guide supplies commands. Where they disagree, follow this policy. Run repository test suites, including Playwright Test suites, through the repository's documented commands.

- Run the installed Google Chrome on every host, never Chrome for Testing, and never run `agent-browser install`. The dotfiles pull sets `executablePath` in `~/.agent-browser/config.json` to it. Where that file or key is missing, pass `--executable-path <installed Chrome>` on `open`, such as `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"` on macOS.
- Give every browser a session name of your own and pass `--session <name>` on every command. Without a name, commands share one default browser with every other agent on the machine. Add a random suffix to the name: `agent-browser session id` derives the same name for every agent in one checkout.
- Close only the sessions you opened, each by name: `agent-browser --session <name> close`.
- Diagnose with `agent-browser doctor`, and leave its `--fix` repairs to the user, because they touch state that other sessions share.
- An idle headless session closes after an hour and discards its tabs. Pass `--idle-timeout <time>` on `open` when a human needs longer.
- Write screenshots, PDFs, HAR files and recordings to explicit paths in a scratch directory.
- Scope snapshots with `-s <css>` or `-d <depth>`, and read the full page when the task needs it.
- Download by clicking: pass `--download-path <scratch-directory>` on `open`, click the link, and wait for the file to appear there. In 0.39.1 the `download` command cancels every download on Windows ([vercel-labs/agent-browser#1659](https://github.com/vercel-labs/agent-browser/issues/1659)) and sends later clicks to its own directory.
- After inspecting the page, run a known sequence of related actions in one `batch --bail` call. Write the steps to a scratch JSON file as an array of argument arrays, such as `[["fill", "#email", "a@example.test"], ["click", "#save"], ["wait", "--text", "Saved"], ["get", "text", "#status"]]`. Pass the file on standard input: `agent-browser --session <name> batch --bail < steps.json`, or in PowerShell `Get-Content -Raw steps.json | agent-browser --session <name> batch --bail`. The JSON form survives shell quoting on every host. End with the expected wait and a check of the resulting state. Keep a snapshot checkpoint whenever the next action depends on what the page shows.
- Pass JavaScript with quotes or several lines on standard input with `eval --stdin`, the same way as a batch file. On Windows, the mise and npm launchers reject or cut off any argument that contains a line break.
- Read plain output; add `--json` when a script parses the result.
- Change the agent-browser version only through the dotfiles mise pin, as Maintenance describes.

Host notes:

- For an existing sign-in, inspect `agent-browser session list` and known task profiles first, and reuse only a session this task owns. Attach to the user's own Chrome or its profile (`--auto-connect`, `--cdp` or `--profile <profile-name>`) only when the user asks for it in this task, because it holds their signed-in sessions. When sign-in is required, keep a dedicated profile directory for it. Google refuses "Sign in with Google" in a browser under automation, so the human signs in once in plain Chrome started without agent-browser. Start it with `--user-data-dir=<directory> --use-mock-keychain --password-store=basic --no-first-run --no-default-browser-check <url>`, which matches the keychain and password store that agent-browser uses. On macOS that is `open -na "Google Chrome" --args` followed by those flags, and elsewhere the installed Chrome with them. Once the human has quit that Chrome, reuse its sign-in with `agent-browser --session <name> --profile <directory> open <url>`. Keep profiles, state files and `--restore` state outside repositories and evidence, and keep cookies and tokens out of output.
- Some sites block headless Chrome, for example with a 403 bot wall. Open that session with `--headed`.
- Paywalled news sites, such as the FT and The New York Times, block DevTools automation, agent-browser included, with bot checks even after the user passes them by hand. On every host, read them with the user's subscriptions through their own Chrome profile and `cua-driver`'s accessibility tree, without asking first. This is the only use of their profile that needs no request in the task. Use the profile that holds the subscriptions: `Default` on macOS. Elsewhere, read the profiles under `profile.info_cache` in Chrome's `Local State`, and ask the user which one when there is more than one. On WSL, drive Chrome on the Windows desktop with the Windows `cua-driver.exe`, because WSL's own `cua-driver` draws on a hidden display. Open a window of your own with `launch_app` for Google Chrome (`com.google.Chrome` on macOS), passing `creates_new_application_instance` and the `additional_arguments` `--profile-directory=<profile>`, `--new-window` and the URL. The running Chrome takes over the request, so find your window by its page title in `list_windows` for Chrome's own process, and act only in that window. Pass the same `session` on every `cua-driver` call, because element tokens belong to the session that read them. To load a page, `set_value` the window's `Address and search bar` field and `press_key` `return` on it. Read the page from `get_window_state`, where body text appears as element values. Never attach DevTools to this profile, through `browser_prepare` or agent-browser, even when `cua-driver` would allow it, because those bot checks block it. Read only a few NYT pages per session, because it shows a bot check after a longer run. Stop at any bot check or CAPTCHA and tell the user. Keep the article text local and out of anything published. On Windows and WSL, which the user's employer manages, also keep it out of files, and delete any scratch copy before you finish. When finished, press your window's close button and call `end_session`. On macOS the close button is the unnamed title-bar button furthest left; `tree_format: "elements"` gives each button's frame. Chrome's `Close Window` menu item is disabled while Chrome is in the background.
- agent-browser runs Chrome on the host where the command runs, so `localhost` reaches that host's dev servers. Windows Chrome also reaches WSL dev servers on `127.0.0.1` through mirrored networking.
- To open a dev server from another host, use an existing task-owned tailnet share or run `tailscale serve <port>` in the foreground. Record the process ID and printed URL. Stop only that process when finished and confirm its URL no longer loads; a foreground share is absent from `tailscale serve status`.
- Codex's in-app browser (`iab`) exists only inside the Codex desktop app.
- Windows: start every session with `scripts/windows-session.ps1 -Session <name> -Url <url>`, in native shells as well as over SSH. Pass further `open` flags with `-LaunchArguments`, for example `-LaunchArguments '--download-path', '<scratch>'`. The helper starts the daemon outside the calling process and gives it files for output. Started any other way, the daemon inherits the caller's output pipes: a captured `open` then hangs until the daemon exits ([#1407](https://github.com/vercel-labs/agent-browser/issues/1407)), and the daemon can crash when it later writes to the closed pipe ([#1993](https://github.com/vercel-labs/agent-browser/issues/1993)). Over SSH, OpenSSH also ends the daemon and its Chrome when the connection exits. Later commands and `close` run normally, over separate SSH calls when remote. If the session has gone, for example after the idle timeout, start it again with the helper. Over SSH, the browser stays invisible to the user.
- To drive an Electron app, or a Chrome this task started with remote debugging, use `agent-browser --session <name> --cdp <port> ...`. When several sessions share that browser, add `--pin-tab` so each keeps its own tab. Load `agent-browser skills get electron` for Electron apps. `close` disconnects and leaves the app running.

## Computer use

Prefer a CLI, an API, or the browser tools when they can do the job. Use desktop control only for native apps and for the paywalled news sites in the browser host notes.

- macOS and Windows: use `cua-driver` through its CLI, or its MCP tools when connected, for Codex and Claude Code alike. Read its own `cua-driver` skill first. Check `cua-driver status` and `cua-driver doctor` before driving an app, then discover the exact app and window with the driver's tools. Use `cua-driver call <tool>` with JSON on standard input for CLI calls. If the daemon is stopped, start the installed one. On macOS run `cua-driver permissions grant`, which launches the installed CuaDriver app by its exact path, so the daemon runs under that app's own Accessibility and Screen Recording grants. If it waits on a macOS prompt, ask the user to approve it. On Windows run `cua-driver autostart kick`. Do not start a second daemon or use Codex Computer Use as a fallback.
- Linux (WSL): the open-source `cua-driver` server's MCP tools, called directly; the `cua-driver` CLI depends on a background service that is stopped here. Its own `cua-driver` skill documents the tools. The server draws on a private virtual display (`:99`), hidden from the user along with any app you launch there.

## Maintenance

The durable source is `skills/browser-and-computer-use` in the dotfiles checkout. Maintain it there and refresh its reviewed source lock before device sync. Tool versions live in `config/mise/config.toml`; host-specific integrations stay in the private configuration. Every host runs the installed Google Chrome through `executablePath` in `~/.agent-browser/config.json`. The dotfiles pull manages only that key, chosen from Google's install paths in `config/agent-browser/chrome.toml`, and blocks on a host without Google Chrome. Leave existing Chrome for Testing downloads in place, because other sessions may still use them. Before upgrading agent-browser, finish or hand back all live sessions. Afterwards, run `agent-browser doctor --offline --quick` on each host and reread `agent-browser skills get core` for changed guidance. Recheck the Windows download workaround when a release fixes #1659. Preserve native computer-use integrations independently of browser updates.

To measure a CLI workflow change, run `python3 <skill-dir>/benchmarks/benchmark.py --output <new-scratch-directory>`. The [probe](benchmarks/benchmark.py) uses a synthetic local form, five interleaved trials per workflow, exact saved-state checks, and owned-session teardown. Its results cover that local flow and CLI bytes only. Keep the CLI's default waits; tune a slower task from its own evidence.
