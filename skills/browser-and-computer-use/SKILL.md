# Browser and computer use

Use only the tools named here.

## Browser

Use Vercel Labs' `agent-browser` from the shell for browser automation, verification, and web development testing on every host, in both Claude Code and Codex. Once per session, load the guide that ships with the installed CLI: `agent-browser skills get core`, adding `--full` for the command reference. Load a specialised guide from `agent-browser skills list`, such as `electron` or `dogfood`, when the task matches it. This shared policy supplies host routing and session ownership; the CLI's guide supplies commands. Where they disagree, follow this policy. Run repository test suites, including Playwright Test suites, through the repository's documented commands.

- Run the installed Google Chrome on every host, never Chrome for Testing, and never run `agent-browser install`. The dotfiles pull sets `executablePath` in `~/.agent-browser/config.json` to it. Where that file or key is missing, pass `--executable-path <installed Chrome>` on `open`, such as `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"` on macOS.
- Give every browser a session name of your own and pass `--session <name>` on every command. Without a name, commands share one default browser with every other agent on the machine. Add a random suffix to the name: `agent-browser session id` derives the same name for every agent in one checkout.
- Close only the sessions you opened, each by name: `agent-browser --session <name> close`.
- Diagnose with `agent-browser doctor`, and leave its `--fix` repairs to the user, because they touch state that other sessions share. Without `--fix` it removes only stale daemon socket, pid and version files, so a queued check can run while other sessions work.
- An idle headless session closes after an hour and discards its tabs. Pass `--idle-timeout <time>` on `open` when a human needs longer.
- A session opened with launch flags, such as `--profile`, `--headed` or `--idle-timeout`, keeps its browser only while every later command passes the same flags, `get url`, `tab list` and `close` included. A command that leaves one out or changes its value restarts the browser and loses the profile's sign-in. On macOS and Linux, run every command through `scripts/ab_session.py`, which saves the flags once per session. On Windows, pass the same flags on every command. Chrome lets one process use a profile folder, so check that the user's own Chrome isn't running on a profile before you pass it to `--profile`.
- Write screenshots, PDFs, HAR files and recordings to explicit paths in a scratch directory.
- Scope snapshots with `-s <css>` or `-d <depth>`, and read the full page when the task needs it.
- To render a page at a set width, such as a 390 px phone, run `set viewport <width> <height>` and then `reload`, and confirm the width with `eval 'window.innerWidth'`. Chrome started headless without agent-browser holds its window at 500 px or wider. For sharp phone images, add the device scale as a third argument, `set viewport 390 900 3`, confirm it with `eval 'window.devicePixelRatio'`, and capture one element with `screenshot <selector> <path>`, which gives a 1170 px-wide image of just that section.
- Headless Chrome reports no hover pointer, so `@media (hover: hover)` rules never apply and a probe measures the touch styles. To test hover styles, pass `--args "--blink-settings=availableHoverTypes=2,primaryHoverType=2,availablePointerTypes=4,primaryPointerType=4"` on `open` and every later command, as the launch-flag bullet above says, and confirm with `eval 'matchMedia("(hover: hover)").matches'`.
- A probe that waits on the page's own timers or `requestAnimationFrame` stalls or reports false misses in a headless tab on a busy machine, because Chrome throttles them. Wait from the driver side, turn on focus emulation, and split a long run, such as by width, so each part ends well inside the shell tool's time limit. For real pointer presses, forced states such as `:hover`, `Emulation.*` settings and awaited evaluations, drive the session's DevTools socket with `node scripts/cdp.mjs`, which attaches to the session's page and turns on focus emulation, rather than writing a driver of your own.
- A harness's own HTML preview tool, such as T3 Code's `html_preview`, renders the HTML string you pass it, not the file on disk. Check a file with agent-browser at `file://<path>`, and keep the preview tool for showing the user a result.
- To check a page's layout, run `scripts/page_check.py <file-or-url>` with Python 3. In a session of its own it measures 390 and 1366 px by default and reports sideways scrolling, elements that stick out, text under 12 px, and labels matching `--nowrap <selector>` that wrap. `--pdf --out <dir>` adds the PDF page count and one contact sheet of the pages. Look at the contact sheet or one screenshot per revision rather than many full-page captures.
- Download by clicking: pass `--download-path <scratch-directory>` on `open`, click the link, and wait for the file to appear there. In 0.39.1 the `download` command cancels every download on Windows ([vercel-labs/agent-browser#1659](https://github.com/vercel-labs/agent-browser/issues/1659)) and sends later clicks to its own directory. For several files from one signed-in site, fetch each inside the page and return it as base64 through `eval --stdin`, because Chrome blocks a site's second and later automatic downloads; stop a download loop after its first miss.
- After inspecting the page, run a known sequence of related actions in one `batch --bail` call. Write the steps to a scratch JSON file as an array of argument arrays, such as `[["fill", "#email", "a@example.test"], ["click", "#save"], ["wait", "--text", "Saved"], ["get", "text", "#status"]]`. Pass the file on standard input: `agent-browser --session <name> batch --bail < steps.json`, or in PowerShell `Get-Content -Raw steps.json | agent-browser --session <name> batch --bail`. The JSON form survives shell quoting on every host. End with the expected wait and a check of the resulting state. Keep a snapshot checkpoint whenever the next action depends on what the page shows.
- In an app with single-key shortcuts, such as mail, send input to a named element inside the `batch --bail` call. Page-level `keyboard type` and `press` go to whatever has focus, so after a failed click they can trigger the app's shortcuts.
- Pass JavaScript with quotes or several lines on standard input with `eval --stdin`, the same way as a batch file. On Windows, the mise and npm launchers reject or cut off any argument that contains a line break.
- Read plain output; add `--json` when a script parses the result.
- Change the agent-browser version only through the dotfiles mise pin, as Maintenance describes.
- "Daemon version mismatch detected, restarting" means two agent-browser versions drove one session. The restart closes its pages and drops every sign-in kept only for that browser session, such as a login held in a session cookie, with no error on the page. An agent shell started before an upgrade keeps the old CLI first on its `PATH`, so before signing in again, compare `agent-browser --version` across each launcher the task uses, such as the shell, PowerShell and Python's `shutil.which`, and call one binary by its path, such as the mise shim.

Host notes:

- For an existing sign-in, inspect `agent-browser session list` and known task profiles first, and reuse only a session this task owns. Attach to the user's own Chrome or its profile (`--auto-connect`, `--cdp` or `--profile <profile-name>`) only when the user asks for it in this task, because it holds their signed-in sessions. When the user has turned remote debugging on at `chrome://inspect`, click Chrome's "Allow remote debugging?" prompt only after they said yes to attaching in this task, and only for a connection you opened. When you finish, offer to turn remote debugging back off, and name any other task that uses it. When sign-in is required, keep a dedicated profile directory for it. Google refuses "Sign in with Google" in a browser under automation, so the human signs in once in plain Chrome started without agent-browser. Start it with `--user-data-dir=<directory> --use-mock-keychain --password-store=basic --no-first-run --no-default-browser-check <url>`, which matches the keychain and password store that agent-browser uses. On macOS that is `open -na "Google Chrome" --args` followed by those flags, and elsewhere the installed Chrome with them. Those two flags belong to a profile directory of your own. The user's own Chrome profile on Linux keeps its cookies in the system keyring (cookie values start with `v11`), so start it without them, because with them it opens signed out. To check that profile's sign-in without starting Chrome, copy its `Default/Cookies` file to a scratch path and look for the site's session cookie names, such as LinkedIn's `li_at`. Once the human has quit that Chrome, reuse its sign-in with `agent-browser --session <name> --profile <directory> open <url>`. Keep profiles, state files and `--restore` state outside repositories and evidence, and keep cookies and tokens out of output.
- To attach to the user's running Chrome with `--auto-connect`, on macOS or Linux, start the session with `scripts/ab_session.py attach <name>`, which saves `--auto-connect --pin-tab` for every later command. When Chrome refuses the session or nobody approves it within 20 seconds, it stops with agent-browser's error and closes the session, so attach again. Without the pin, a tab the user opens takes over the session, and your next read is of their page. Each new attach asks the user to click Allow again, so hold one session across a block of work and batch the steps that need it. On Linux, once the user has said yes to attaching in this task, approve the prompts yourself with `scripts/ab_session.py attach --approve <name>`, which runs the attach under `scripts/approve_attach.py` and needs `uv`. It works only on a Chrome that was started with `--force-renderer-accessibility`, as `x-browser` starts it, because Chrome shows its windows to accessibility tools only then. On a Chrome the user opened themselves it exits 4 before it attaches and raises no prompt: run the attach without `--approve` and ask the user to click Allow, or ask them to restart Chrome with the flag. On 11 November 2026, before that check, such an attach found no prompt to press, timed out and left its prompt over the user's window, and two test Chromes showed the flag makes the difference. It finds Chrome's browser process from the default profile's `SingletonLock`; for another profile pass `--approve=<pid>`. It presses only the Allow buttons that appear while the attach runs and leaves earlier prompts alone, because those belong to other connections. Chrome ignores a press that lands as its prompt appears, so the script presses again while the prompt stays. On WSL on 10 November 2026, with agent-browser 0.42.0, one attach raised two prompts. Without the second press 2 of 6 test attaches hung on an ignored press, and with it 17 of 17 attached. A prompt nobody approved stays on screen until the user cancels it. The same day, with 0.41.2 and 0.42.0, an attach nobody approved also left a daemon that ignored `close`, so `ab_session.py close <name>` now stops that session's own daemon when agent-browser's close fails. Never press Allow or Cancel by name, since several prompts can be stacked. The attached session is pinned to a new `about:blank` tab. `tab list` leaves out Chrome's own pages, such as the New Tab page, and an attach to a Chrome that shows only those opens a second blank tab that stays behind, so start Chrome on a web page (tested 10 November 2026). Close that tab with `tab close <its id>` before `close`, because `close` only detaches and leaves their Chrome running. `window new` opens a signed-out window, so to get one in their profile run `google-chrome --user-data-dir=<profile> --new-window <url>`.
- When WebFetch, curl, or headless agent-browser gets a 403, a Cloudflare check, or another bot wall on a page you need, open an agent-browser session with `--headed`, which passes many of them. For public documentation, also try the routes that need nothing of the user's: a web search limited to the site's domain to find each page's address, the site's `/llms.txt` or a `.md` version of the page, and an exact-URL Internet Archive copy at `https://web.archive.org/web/<year>/<url>`, which redirects to the nearest copy and returned the page on 9 November 2026. Fetch it with curl's `--compressed`, because the archive can send it gzipped. Quote only the page text you saved, never a search tool's summary of it. If the page still won't load, ask the user whether to read it in their own Chrome with `scripts/read_page.py`. For a file a deliverable will quote, such as a PDF, make the same offer before you settle for an abstract or a weaker source, because the user's own Chrome often passes the check unaided. Tell the user which facts you could not read at the source instead of filling them from third-party summaries.
- Public X or Twitter posts and long articles need no browser. `curl -s https://api.fxtwitter.com/status/<id>` returns one as JSON with no login, with a long article's text under `tweet.article.content.blocks`. It is a third-party service, so check that the JSON's `code` is 200, and open an agent-browser session when it is down.
- Paywalled news sites, such as the FT and The New York Times, block DevTools automation, agent-browser included, with bot checks even after the user passes them by hand. On every host, read them with the user's subscriptions through their own Chrome profile and `cua-driver`'s accessibility tree, without asking first. This is the only use of their profile that needs no request in the task. With Chrome running, run `scripts/read_page.py URL...` with Python 3. It opens one window of its own, reads each page, stops at a bot check or CAPTCHA, closes its window and ends its `cua-driver` session. Pass `--profile` with the profile that holds the subscriptions: `Default`, its default, on macOS. Elsewhere, read the profiles under `profile.info_cache` in Chrome's `Local State`, and ask the user which one when there is more than one. On WSL, pass `--cua cua-driver.exe` to drive Chrome on the Windows desktop, because WSL's own `cua-driver` draws on a hidden display. Never attach DevTools to this profile, through `browser_prepare` or agent-browser, even when `cua-driver` would allow it, because those bot checks block it. The accessibility tree that `read_page.py` reads hides link URLs, so take article URLs from the NYT sitemap index (`https://www.nytimes.com/sitemaps/new/sitemap.xml.gz`, which lists monthly sitemaps of article URLs) or an FT stream's RSS (`https://www.ft.com/<stream>?format=rss`), not from site search. Read only a few NYT pages per task, because it shows a bot check after a longer run or a few searches; the script refuses more than five in one run. When the script stops at a bot check, tell the user. If you go around a rule in this skill, quote its stated reason when you report that, and ask one direct question. `--out DIR` saves each page to a file. On Windows and WSL, each page opens in a window of its own, because Windows refuses the address bar's Return key in the background, and a table prints one cell per line, because Windows' accessibility tree hides table rows.
- For any other page the user asks you to read in their own Chrome, use the same script, and add `--expand` to open collapsed FAQ answers first. It reads only the page, never the tab strip or the user's other windows, prints each table row on one line, and skips a page whose address bar shows another site. Open no URL in the user's Chrome with `cua-driver launch_app` and `urls`, which adds a tab to their front window. Pass `--out DIR` when the text feeds a deliverable, so the source survives a compaction. When one Chrome profile holds several accounts of an app, open the app with an account hint, such as `https://outlook.office.com/mail/?login_hint=<address>`, and assert the signed-in address on the page before the first search or capture.
- agent-browser runs Chrome on the host where the command runs, so `localhost` reaches that host's dev servers. Windows Chrome also reaches WSL dev servers on `127.0.0.1` through mirrored networking.
- On WSL, Windows Chrome and WSL's Chrome are separate browsers, each with its own network and profiles. When a read through Windows Chrome returns nothing, test the Windows host's network with a TCP check through interop, such as `powershell.exe -NoProfile -Command '(Test-NetConnection example.com -Port 443).TcpTestSucceeded'`, before retrying with longer waits. Send no web request from Windows for this, such as `curl.exe` or `Invoke-WebRequest`, because endpoint security can flag it and isolate the machine. Then try a `--headed` agent-browser session in WSL, whose window shows on the user's desktop, before you report the page as blocked. Tell the user before you use a host or profile other than the one they approved.
- Approval to use a signed-in profile covers the sites the user named. Open any other site in a dedicated profile of your own, or ask first, because every page that profile loads runs beside its signed-in sessions.
- To open a dev server from another host, use an existing task-owned tailnet share or run `tailscale serve <port>` in the foreground. Record the process ID and printed URL. Stop only that process when finished and confirm its URL no longer loads; a foreground share is absent from `tailscale serve status`. For a share that outlives the session, such as one for the user's phone, follow `work-across-tailscale-machines`.
- Codex's in-app browser (`iab`) exists only inside the Codex desktop app.
- Windows: start every session with `scripts/windows-session.ps1 -Session <name> -Url <url>`, in native shells as well as over SSH. Pass further `open` flags with `-LaunchArguments`, for example `-LaunchArguments '--download-path', '<scratch>'`. The helper starts the daemon outside the calling process and gives it files for output. Started any other way, the daemon inherits the caller's output pipes: a captured `open` then hangs until the daemon exits ([#1407](https://github.com/vercel-labs/agent-browser/issues/1407)), and the daemon can crash when it later writes to the closed pipe ([#1993](https://github.com/vercel-labs/agent-browser/issues/1993)). Over SSH, OpenSSH also ends the daemon and its Chrome when the connection exits. Later commands and `close` run normally, over separate SSH calls when remote. If the session has gone, for example after the idle timeout, start it again with the helper. Over SSH, the browser stays invisible to the user. An `open --profile` that fails with `Chrome exited early (exit code: 0) without writing DevToolsActivePort` means another Chrome holds that profile: close the session that owns it by name, and keep its `%USERPROFILE%\.agent-browser\<session>.*` files while `agent-browser session list` still shows it, because deleting them leaves its daemon and Chrome running with the profile locked. A `get url` that returns `chrome-error://` after a successful `open` means the page didn't load.
- To drive an Electron app, or a Chrome this task started with remote debugging, use `agent-browser --session <name> --cdp <port> ...`. When several sessions share that browser, add `--pin-tab` so each keeps its own tab. Load `agent-browser skills get electron` for Electron apps. `close` disconnects and leaves the app running. Record that Chrome's main process ID when you start it, and stop it by that ID after `/proc/<pid>/cmdline` shows your profile and port, then wait on the same ID, because a `pgrep -f` or `pkill -f` for its flag also matches your own command. To run an Electron agent app unattended, find its prompt deep links by searching its `app.asar` for `scheme://` strings, open one in the app's own environment, press Send through accessibility, and detect the end of the run from the app's session logs rather than its window.

## Computer use

Prefer a CLI, an API, or the browser tools when they can do the job. Use desktop control only for native apps and for reading pages in the user's own Chrome, as the browser host notes describe. When a value exists only in an app's window, or you are about to give the user click steps, drive the app yourself, including to clean up a tool you installed. Before you say a product lacks a control or that you can't reach one, look at its other surfaces, such as its desktop app, its config file, its local install and the Windows-side driver, and name the ones you checked in that sentence. That covers a consent or permission prompt inside an action the user has approved: say what the prompt grants, offer in the same message to click it yourself, and act on their yes. Before you ask the user to paste or retell mail or chat content, offer to read it in the app, and wait for their yes because it is private. If an app you launched shows no accessibility tree, check your own launch first: an app started inside its own `dbus-run-session` shows none until accessibility is enabled on that bus (`org.a11y.Status` `IsEnabled`, `ACCESSIBILITY_ENABLED=1`) and cua-driver runs with the same `DBUS_SESSION_BUS_ADDRESS`.

- macOS and Windows: use `cua-driver` through its CLI, or its MCP tools when connected, for Codex and Claude Code alike. Read its own `cua-driver` skill first. Check `cua-driver status` and `cua-driver doctor` before driving an app, then discover the exact app and window with the driver's tools. Use `cua-driver call <tool>` with JSON on standard input for CLI calls. For a `run_script` flow, write the script to a file and run `node scripts/cua-js.mjs <file>`, which prints only its console output and return value, or its error with the script line; `--calls` adds the per-call log. Pass one named `session` on every call of a flow that acts on an element token from an earlier call, because a token belongs to the session that read it, and a call without one runs in a throwaway session that refuses the token as stale. Otherwise leave `--session` out, because a named session expires after five idle minutes. An expired label rejects every call, reads included, with exit 1, empty stdout and the reason on stderr, so read stderr and carry on under a new label. If the daemon is stopped, start the installed one. On macOS run `cua-driver permissions grant`, which launches the installed CuaDriver app by its exact path, so the daemon runs under that app's own Accessibility and Screen Recording grants. If it waits on a macOS prompt, ask the user to approve it. On Windows run `cua-driver autostart kick`. Do not start a second daemon or use Codex Computer Use as a fallback. Chrome's Save As dialog on Windows is a separate top-level window with its own PID, so send `press_key` `return` to that window, then confirm the file on disk, because the effect reports as unverifiable.
- Linux (WSL): the open-source `cua-driver` server's MCP tools, called directly; the `cua-driver` CLI depends on a background service that is stopped here. Its own `cua-driver` skill documents the tools. The server draws on a private virtual display (`:99`), hidden from the user along with any app you launch there. To drive an app on the Windows desktop from WSL, run `cua-driver.exe call <tool> '<json>'` through interop instead. Its guide is at `/mnt/c/Users/<user>/.claude/skills/cua-driver/WINDOWS.md`, because the WSL install carries only the Linux guide.
  - The WSLg windows the user sees are on display `:0`, and the configured server on `:99` lists none of them. Reach them with a second `cua-driver mcp` over stdio, started with `DISPLAY=:0`, the session's `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS`, and the configured server's cua-driver settings, and do each read and the action that uses its tokens in that one process, because tokens end with it. When the user need not watch, have them sign in on `:0`, then run the app with the same profile on `:99`. A daemon of your own on `:0` also works and keeps tokens between calls made under one named session: start it with `DISPLAY=:0 setsid -f cua-driver serve --socket <scratch>/cua.sock --pid-file <scratch>/cua.pid`, call it with `cua-driver call --socket <scratch>/cua.sock <tool> '<json>'`, and stop it by that PID when done.
  - WSLg has no active window, so `foreground_unavailable` and `background_unavailable` there are cua-driver's own checks, and no input was sent. An element click by role and name works on a row whose action is `press`. For a row whose only action is `check` or `select`, such as a toggle or menu item, call AT-SPI `org.a11y.atspi.Action.DoAction` on that element with `gdbus`, on the bus that `org.a11y.Bus.GetAddress` returns. Enter prompt text through the app's deep link where `set_value` has no route. A submenu that opens only on hover is out of reach, so that one step goes to the user.
  - Chrome on `:0` refuses background scrolling, and its address bar has no value route. Open a page with `google-chrome --user-data-dir=<profile> <url>`, with `DISPLAY=:0` and `WAYLAND_DISPLAY` unset, which hands it to the running Chrome as a new tab. Close that tab with `DoAction` on the `Close` button under its `page tab`, and only tabs you opened. Page a list that loads as you scroll by calling `org.a11y.atspi.Component.ScrollTo` with `6` on its last loaded row, with that tab in front. `org.a11y.atspi.Hyperlink.GetURI` with `0` returns a link's full address. A script that walks the tree needs one D-Bus connection, such as `uv run --with jeepney`, rather than a `gdbus` call per node, and can skip `document web` nodes when it only needs the tab strip.
  - Chrome exposes only each window's active tab as a named `frame`, so a tab that another agent brings forward in a shared window drops out of the tree. Read a long-lived page from a window of your own. cua-driver's walk of a Chrome process covers every window, and with two windows of identical bounds it returned the other window's tree and timed out. Read the tab's `frame` directly over AT-SPI instead, matched by Chrome's process ID and the frame's name.
  - From the Windows side, `cua-driver.exe` can click and paste into a WSLg window in the background. Every WSLg window is an `msrdc.exe` window sharing one process ID, with an empty accessibility tree, so `list_windows` with an `app` filter returns nothing: list by `pid` or with `{}`, match the title ending in the distro's name, and click by pixel from a fresh screenshot. Serve the text with `setsid xclip -selection clipboard -loops 0 -i <file>` on `DISPLAY=:0`, confirm it with `xclip -o | cmp`, then send the click and `hotkey` `ctrl,v` in one `run_steps`, and look at the window to see that the text arrived.
  - Chrome on `:0` takes no typed text from the Linux `cua-driver`: its fields expose no writable text interface, and that driver sends no keystrokes there. To fill a field in the user's own Chrome, ask them to switch on remote debugging at `chrome://inspect/#remote-debugging`, which Chrome won't open from a command line, and to answer its "Allow remote debugging?" prompt. Then pass the text on standard input to `scripts/cdp_insert_text.py`, which prints only whether the field holds it, so it suits a secret from a private prompt. Press buttons, and switch the setting back off afterwards, with `scripts/atspi_do.py`, which runs an element's own action and refuses when more than one element matches: `--role 'check box' --name '^Allow remote debugging' --action uncheck`, with the inspect tab in front. cua-driver's `get_window_state` stops a Chrome read after one second by default, so pass a larger `timeout_ms` when rows seem to be missing.
  - A chat list that loads as you scroll returns rows outside the view as empty placeholders. Save one record per message row from each view and merge the views by date separator and order, not by matching lines. WhatsApp Web loads older history only while the phone is online, so ask the user to bring it online at the first request for older messages that brings nothing.
  - Send input only through these routes. Raw input, such as XTEST through ctypes or `xdotool type`, goes to whichever window has focus, not to your target, and so does `cua-driver.exe` in foreground delivery, which reports success while the keystrokes land elsewhere, such as in Windows' Start search. Stop after the first input with no visible effect, and find out where it went before you send more.
- A loop that polls a window or page, or an agent-browser loop that measures one page after another, checks each step's exit status and that the window ID or URL is still its target before it counts the result. A failed capture that recopies the last image makes a dead window look idle, a session moved to another tab reports a false finish, and a failed `open` leaves the previous page loaded, so assert `location.pathname` on every row and count the distinct pages measured against those expected.
- Leave a window the user already has open as it is, even when it is stuck. To get past a stuck state such as a PIN dialog, open a temporary window of your own, because a reload can leave theirs blank.
- Windows apps:
  - Admin-only programs: `launch_app` starts them without admin rights. Start one with `Start-Process <path> -Verb RunAs` from PowerShell, have the user approve the prompt, then drive its windows. A daemon running as admin can also read and click admin windows, and `check_permissions` shows its `integrity_level`, so check that before assuming they are blocked.
  - Store apps: `launch_app({aumid})` can return a process with no windows while another process owns the window. Find the window with `list_windows({})` by title and app name. `Get-StartApps` lists the AUMIDs.
  - Toggles in a WebView2 app: read with `tree_format:"both"`, match the row on `label` and `role`, and read `selected`, because the markdown tree shows no on/off state. The tree fills in over several reads, so re-read until the row count stops growing. A click's `effect:"unverifiable"` proves nothing, so confirm by the flip in `selected`.
  - Pixel clicks: read the window in the same named session before each pixel click, or the driver refuses it with `screenshot_context_missing`. A script or wrapper around cua-driver calls prints each call's error or refusal field, so a refused click shows as failed.
  - Virtualised lists in a Chromium or WebView2 app, such as a chat: background `scroll` returns `background_unavailable`. To page in the background, read the window, then pixel-click the scrollbar track, and read again before the next click, because each pixel click needs a fresh read.
  - Settings: compare the whole settings group before and after a change, because vendor settings can be mutually exclusive and turn each other off.
  - Electron apps with no accessibility tree, such as the Claude desktop app, which is how a message reaches an agent session running there: on 11 November 2026 its window returned no tree, a background pixel click worked, and text arrived only in the foreground. Read it with `get_window_state` and `include_accessibility_tree:false`, and read again when the capture times out. Put text into its message box with `python3 -I scripts/win_paste.py --pid <pid> --window-id <id> --x <x> --y <y> < file` from WSL, with `--replace` when the box may hold text and with a time limit of 4 minutes. It pastes only once the clipboard holds the text, puts the user's clipboard text back afterwards, and brings the window to the front for a moment, so tell the user first. It exits 3 and changes nothing when the clipboard holds more than plain text, such as an image or a copy from a browser, and a clipboard that was empty holds the pasted text afterwards.   - Key combinations: a background `hotkey` can report success while the window receives the letters alone.   - A test window: Windows 11's Notepad reopens the files of its last session, so a Notepad you launch can show the user's documents, and a read of its tree returns their text. Test input in a window of your own instead, such as a PowerShell `System.Windows.Forms` form with one `RichTextBox`.

## Maintenance

The durable source is `skills/browser-and-computer-use` in the dotfiles checkout. Maintain it there and refresh its reviewed source lock before device sync. Tool versions live in `config/mise/config.toml`; host-specific integrations stay in the private configuration. Every host runs the installed Google Chrome through `executablePath` in `~/.agent-browser/config.json`. The dotfiles pull manages only that key, chosen from Google's install paths in `config/agent-browser/chrome.toml`, and blocks on a host without Google Chrome. Leave existing Chrome for Testing downloads in place, because other sessions may still use them. Before upgrading agent-browser, finish or hand back all live sessions. Afterwards, run `agent-browser doctor --offline --quick` on each host and reread `agent-browser skills get core` for changed guidance. On Linux, after an agent-browser or Chrome upgrade and after a change to `scripts/ab_session.py` or `scripts/approve_attach.py`, also run `python3 scripts/attach_selftest.py`. It attaches five times to a throwaway Chrome profile of its own, which opens a Chrome window on the desktop for about a minute, and exits 0 when every attach worked. The scripts' unit tests run against stand-ins, so only this shows that a new Chrome or agent-browser still behaves as they expect. Recheck the Windows download workaround when a release fixes #1659. Preserve native computer-use integrations independently of browser updates. Update cua-driver by the steps under Updating in `config/cua-driver/README.md` in the private dotfiles repository, and never run `cua-driver update --apply` or the vendor's install script directly on WSL or Windows. As read in the vendor's install scripts on 10 November 2026, they stop every running `cua-driver` process on the machine, which cuts the driver connection of other agent sessions, and on Windows they download with PowerShell web cmdlets, which the user's rules forbid on that PC.

To measure a CLI workflow change, run `python3 <skill-dir>/benchmarks/benchmark.py --output <new-scratch-directory>`. The [probe](benchmarks/benchmark.py) uses a synthetic local form, five interleaved trials per workflow, exact saved-state checks, and owned-session teardown. Its results cover that local flow and CLI bytes only. Keep the CLI's default waits; tune a slower task from its own evidence.
