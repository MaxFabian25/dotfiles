# Attach to the user's running Chrome

To attach to the user's running Chrome with `--auto-connect`, on macOS or Linux, start the session with `scripts/ab_session.py attach <name>`, which pins it to a new `about:blank` tab, because without the pin a tab the user opens takes over the session and your next read is of their page. Run `scripts/ab_session.py` with no command for its commands, its exit statuses and what its `close` does. Each new attach asks the user to click Allow again, so hold one session across a block of work and batch the steps that need it. On Linux, once the user has said yes to attaching in this task, approve the prompts yourself with `scripts/ab_session.py attach --approve <name>`. It works only on a Chrome started with `--force-renderer-accessibility` and with `ACCESSIBILITY_ENABLED=1` in its environment, unless the desktop's AT-SPI switch was on as it started, as Omarchy's app launcher starts the user's Chrome. When it exits 4, its message names what that Chrome lacks, and the attach raised no prompt: run the attach without `--approve` and ask the user to click Allow, or on WSL press it yourself from the Windows side as [wslg.md](wslg.md) says, or ask them to restart Chrome that way. A prompt nobody approved stays on screen until the user cancels it (11 November 2026). Never press Allow or Cancel by name, since several prompts can be stacked: on WSL on 10 November 2026, with agent-browser 0.42.0, one attach raised two. `tab list` leaves out Chrome's own pages, such as the New Tab page, and an attach to a Chrome that shows only those opens a second blank tab that stays behind, so start Chrome on a web page (tested 10 November 2026). Close that tab with `tab close <its id>` before `close`, because `close` only detaches and leaves their Chrome running. `window new` opens a signed-out window, so to get one in their profile run `google-chrome --user-data-dir=<profile> --new-window <url>`.
