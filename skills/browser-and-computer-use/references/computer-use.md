# Computer use host and input rules

Read this before driving a native app with `cua-driver`, reading a WSLg window on display `:0`, sending keys or pasting into a Windows or Electron app, or polling windows in a loop.

- macOS and Windows: before you drive an app with `cua-driver`, read [cua-driver-hosts.md](cua-driver-hosts.md). Do not start a second daemon or use Codex Computer Use as a fallback.
- Linux (WSL): the open-source `cua-driver` server's MCP tools, called directly; the `cua-driver` CLI depends on a background service that is stopped here. Its own `cua-driver` skill documents the tools. The server draws on a private virtual display (`:99`), hidden from the user along with any app you launch there. To drive an app on the Windows desktop from WSL, run `cua-driver.exe call <tool> '<json>'` through interop instead. Its guide is at `/mnt/c/Users/<user>/.claude/skills/cua-driver/WINDOWS.md`, because the WSL install carries only the Linux guide.
  - To read or drive a window the user sees, a WSLg window on display `:0` such as their Chrome, read [wslg.md](wslg.md) first. It covers a second `cua-driver` on `:0`, AT-SPI actions, Chrome on `:0`, and clicking, pasting and reading back through `cua-driver.exe` from the Windows side.
  - Send input only through the routes this skill and that file name. Raw input, such as XTEST through ctypes or `xdotool type`, goes to whichever window has focus, not to your target, and so does `cua-driver.exe` in foreground delivery, which reports success while the keystrokes land elsewhere, such as in Windows' Start search. Stop after the first input with no visible effect, and find out where it went before you send more.
- A loop that polls a window or page, or an agent-browser loop that measures one page after another, checks each step's exit status and that the window ID or URL is still its target before it counts the result. A failed capture that recopies the last image makes a dead window look idle, a session moved to another tab reports a false finish, and a failed `open` leaves the previous page loaded, so assert `location.pathname` on every row and count the distinct pages measured against those expected.
- Leave a window the user already has open as it is, even when it is stuck. To get past a stuck state such as a PIN dialog, open a temporary window of your own, because a reload can leave theirs blank.
- Windows apps:
  - For admin-only programs, Store apps, toggles in a WebView2 app, pixel clicks, virtualised lists in a Chromium or WebView2 app, and vendor settings, read [windows.md](windows.md).
  - Electron apps with no accessibility tree, such as the Claude desktop app, which is how a message reaches an agent session running there. Read it with `get_window_state` and `include_accessibility_tree:false`, and read again when the capture times out. Put text into its message box with `python3 -I scripts/win_paste.py --pid <pid> --window-id <id> --x <x> --y <y> < file` from WSL, with `--replace` when the box may hold text and with a time limit of 4 minutes; its `--help` gives its exit statuses and what it does with the user's clipboard. It brings the window to the front for a moment, so first run `win-presence --away-after 5` on WSL, which reads whether the user is at the PC; the user chose 5 idle minutes on 2026-11-15 over 15, accepting that a user reading the screen gives no input. On exit 3, away, paste without asking. On exit 0, present, or any code other than 0 and 3, which counts as unknown, ask through the question tool and wait for the user's word that they are not typing, because a user at the desktop is not reading the chat. Then look at the window and click the app's send button in the background. Leave `type_text` in the foreground alone there: it stopped after 224 of 799 characters when the user clicked another window.
  - Key combinations: a background `hotkey` can report success while the window receives the letters alone. A WinForms text box received "av" for Ctrl+A and Ctrl+V on 11 November 2026, so read the field back. The driver's own guide says to try the background first and go to the foreground only on a refusal, which this case never gives, so where the window has no tree to read back, pass `delivery_mode:"foreground"` for the combination from the start.
  - Foreground input: a foreground `scroll` or key goes to whichever window is in front when it arrives. Run `win-presence --away-after 5` first, as for `win_paste.py` above: on exit 3 send the input without asking, and on any other code only after the user's word, since every code other than 0 and 3 counts as unknown. Send it in one `run_steps` call right after `bring_to_front` on the target, and check that `landed_on_target` is true. After typing, capture the window again a few seconds later before you type again, because a capture can show the screen from before the input.
  - A test window: Windows 11's Notepad reopens the files of its last session, so a Notepad you launch can show the user's documents, and a read of its tree returns their text. Test input in a window of your own instead, such as a PowerShell `System.Windows.Forms` form with one `RichTextBox`.
