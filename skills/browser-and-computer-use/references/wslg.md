# WSLg windows on the user's desktop, from WSL

The `browser-and-computer-use` skill sends you here before you read or drive a window the user sees from WSL, such as their Chrome or another WSLg app on display `:0`. Script paths are relative to the skill's folder.

- The WSLg windows the user sees are on display `:0`, and the configured server on `:99` lists none of them. Reach them with a second `cua-driver mcp` over stdio, started with `DISPLAY=:0`, the session's `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS`, and the configured server's cua-driver settings, and do each read and the action that uses its tokens in that one process, because tokens end with it. When the user need not watch, have them sign in on `:0`, then run the app with the same profile on `:99`. A daemon of your own on `:0` also works and keeps tokens between calls made under one named session: start it with `DISPLAY=:0 setsid -f cua-driver serve --socket <dir>/cua.sock --pid-file <dir>/cua.pid`, call it with `cua-driver call --socket <dir>/cua.sock <tool> '<json>'`, and stop it by that PID when done. Make `<dir>` short, such as a folder from `mktemp -d` under `/tmp`, as the skill's socket-path bullet says: on 11 November 2026 a `--socket` deep in a run folder made `serve` exit 1, and every later call said only "daemon is not running".
- WSLg has no active window, so `foreground_unavailable` and `background_unavailable` there are cua-driver's own checks, and no input was sent. An element click by role and name works on a row whose action is `press`. For a row whose only action is `check` or `select`, such as a toggle or menu item, call AT-SPI `org.a11y.atspi.Action.DoAction` on that element with `gdbus`, on the bus that `org.a11y.Bus.GetAddress` returns. Enter prompt text through the app's deep link where `set_value` has no route. A submenu that opens only on hover is out of reach, so that one step goes to the user.
- Chrome on `:0` refuses background scrolling, and its address bar has no value route. Open a page with `google-chrome --user-data-dir=<profile> <url>`, with `DISPLAY=:0` and `WAYLAND_DISPLAY` unset, which hands it to the running Chrome as a new tab. Close that tab with `DoAction` on the `Close` button under its `page tab`, and only tabs you opened. Page a list that loads as you scroll by calling `org.a11y.atspi.Component.ScrollTo` with `6` on its last loaded row, with that tab in front. `org.a11y.atspi.Hyperlink.GetURI` with `0` returns a link's full address. A script that walks the tree needs one D-Bus connection, such as `uv run --with jeepney`, rather than a `gdbus` call per node, and can skip `document web` nodes when it only needs the tab strip.
- Chrome exposes only each window's active tab as a named `frame`, so a tab that another agent brings forward in a shared window drops out of the tree. Read a long-lived page from a window of your own. cua-driver's walk of a Chrome process covers every window, and with two windows of identical bounds it returned the other window's tree and timed out. Read the tab's `frame` directly over AT-SPI instead, matched by Chrome's process ID and the frame's name.
- From the Windows side, `cua-driver.exe` can click and paste into a WSLg window in the background. Every WSLg window is an `msrdc.exe` window sharing one process ID, with an empty accessibility tree, so `list_windows` with an `app` filter returns nothing: list by `pid` or with `{}`, match the title ending in the distro's name, and click by pixel from a fresh screenshot. Serve the text with `setsid xclip -selection clipboard -loops 0 -i <file>` on `DISPLAY=:0`, confirm it with `xclip -o | cmp`, then send the click and `hotkey` `ctrl,v` in one `run_steps`, and look at the window to see that the text arrived.
- A WSLg window that `cua-driver.exe`'s `list_windows` places at x -32000 is minimised. Restore it yourself with `bring_to_front` on its `pid` and `window_id`, which landed on its target on 7 November 2026. Once the user has said yes to an attach in this task, press a Chrome "Allow remote debugging?" prompt by pixel from a fresh screenshot, as an agent did that day, but only when no such prompt was on screen before your attach began, because a pixel press can't tell your prompt from one stacked for another connection.
- To read a chat app's reply back, click its Copy button and read `xclip -selection clipboard -o` on `DISPLAY=:0`. To get its files, download each from its card's menu, which saves into `~/Downloads`, and list that folder before and after. On 6 November 2026 this brought back a 3,385-byte reply and three files through background clicks, with no click steps from the user.
- Chrome on `:0` takes no typed text from the Linux `cua-driver`: its fields expose no writable text interface, and that driver sends no keystrokes there. To fill a field in the user's own Chrome, ask them to switch on remote debugging at `chrome://inspect/#remote-debugging`, which Chrome won't open from a command line, and to answer its "Allow remote debugging?" prompt, or press it yourself as the bullet on minimised windows says. Then pass the text on standard input to `scripts/cdp_insert_text.py`, which prints only whether the field holds it, so it suits a secret from a private prompt. Press buttons, and switch the setting back off afterwards, with `scripts/atspi_do.py`, which runs an element's own action and refuses when more than one element matches: `--role 'check box' --name '^Allow remote debugging' --action uncheck`, with the inspect tab in front. cua-driver's `get_window_state` stops a Chrome read after one second by default, so pass a larger `timeout_ms` when rows seem to be missing.
- A chat list that loads as you scroll returns rows outside the view as empty placeholders. Save one record per message row from each view and merge the views by date separator and order, not by matching lines. WhatsApp Web loads older history only while the phone is online, so ask the user to bring it online at the first request for older messages that brings nothing.
