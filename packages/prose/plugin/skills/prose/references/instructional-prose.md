# Instructional prose

Apply this branch to an instruction, procedure, requirement, warning, or caution.

## Procedures

- Write instructions in the imperative form. Name the action directly.
- Use *install* for the action in an instruction. Use *installation* for a named procedure or
  result. Write *perform a clean or custom installation*, not *do an installation*. Preserve
  product commands and defined technical terms.
- Preserve *please* in a genuine request for permission or forgiveness, correspondence, quotation,
  or source text.
- Put every required starting state, tool, input, permission, and access condition before the
  first procedural action.
- Document one primary input method. If several methods are available to the intended readers,
  choose the shortest, simplest path.
- Include an alternative only when a supported input method, stated reader constraint, or failure
  condition requires it.
- Within one procedure, refer to an earlier repeated action only when readers can identify it
  without searching.
- In a procedure, put one action in each sentence unless the actions occur at the same time.
- State a procedural goal before the action when the goal helps the reader choose or understand it.
- Describe an observable event instead of assuming that a reader sees, hears, or speaks. Retain
  sensory wording when the sense is the action, the wording is exact, or a common expression remains
  clear.
- Put any condition or context needed to apply an instruction before its action. State an expected
  result separately in the same step when it helps readers recognise completion or choose the next
  step.
- Begin an optional procedural step with *Optional:*. Begin a conditional step with its condition.
- Replace *if necessary* with the observable circumstance that requires the action.
- Keep information in notes. Keep each instruction, limit, permission, and result in its work step.
- Keep a numbered procedure contiguous. Put explanations inside a step or outside the sequence.
- Review a procedure with more than 12 top-level steps. Split it only at a stable pause point.
- Give each vertical list one function. Separate procedural and descriptive lists.

## Requirement language

- Use *must* only for a required action and *should* only for a recommendation.
- Use *may* for permission and *can* for possibility or capability.
- State an obligation with the applicable modal or as a factual dependency.
- Use *must not* for a prohibition and *cannot* for impossibility or lack of capability.
- Use the imperative *Do not* for a procedural prohibition.

## Requirements

- End a requirement, procedure, or complete inventory without an open-ended marker.
- Write each requirement with an observable condition, measure, or explicit judgement.
- Put one individually verifiable requirement in each sentence.
- State a requirement before its rationale. Put the rationale in a separate sentence.

## Warnings and cautions

- Use each labelled notice only for its host or governing domain's defined purpose. Keep routine
  information in the main flow.
- Use *Important* only when the host defines it for a significant non-safety obstacle to successful
  completion.
- Use labelled warnings and cautions only for material risks, such as injury, equipment or software
  damage, and data loss. Apply the governing domain's classification.
- Identify the risk level with the word or symbol required by the governing domain. In aerospace
  and defence, a warning identifies possible injury or death. A caution identifies possible damage
  to objects.
- Start a safety instruction with a clear command or a condition the reader must know before the
  action.
- After the command or condition, explain the risk or possible result.
- Put each notice at the affected action or condition. Do not stack repeated notices or use a
  notice as visual emphasis.

Complete this branch when each instruction states its action and any condition needed to apply it.
Include an expected result when readers need it to recognise completion or choose the next step.
Each requirement uses the correct modal and makes any condition explicit.
